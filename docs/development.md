# 改造协作规则

本规则约束 Agora 的开发团队，不是产品运行时协议。产品目标与实施授权见[工作台计划](canvas-workbench-plan.md)。[GitHub Issues](https://github.com/arvakme/agora/issues) 是任务事实源，[Project](https://github.com/users/arvakme/projects/2) 是其进度视图。

## 工单到交付

1. **确认范围。** 主持人核对最新代码、未提交改动和依赖工单；把目标、允许路径、共享接口、清理责任、未决假设和可观察 Done 写入 Issue。用户只确认讨论时不启动实现；新问题由主持人决定归入原单或另开单。
2. **认领后派发。** 主持人在 Issue 留下领取记录，注明实际执行者、模型/权限、pane、路径和基线提交；再通过 seedmux-team 创建或复用真实 CLI pane。共同使用一个 GitHub 账号时，Assignee 只代表账号，不冒充多个独立开发者。
3. **按依赖并行。** 共享接口、类型、schema 和注册入口先由一个写者落定；无依赖且路径不重叠的工单并行。Seedmux 工单只带 Issue 引用和执行上下文，回执是证据，不另维护任务验收状态。
4. **窄测与回执。** 执行者完成允许范围内的修改及必要清理，运行最窄受影响验证，提交结论、diff、命令裸退出码和未决项。涉及范围外的问题回报主持人；不擅自开单、清理他人改动或宣布验收完成。
5. **统一审查。** 主持人亲自检查最终 diff 和证据；复杂或影响大的实现交给非作者独立对抗审查，修复后重验。不得用同账号的一条自批评论冒充独立 PR approval。
6. **实测与合入。** 针对候选提交完成真实终端/后端验收；存在界面时按下节进行浏览器 dogfood。PR 关联 Issue，通过必要 CI、审查和实测门才启用自动合并，不使用管理员绕过。检查必须对应当前 PR head，新的代码提交使相关验收失效。
7. **确认完成。** 看见合并和 main 上必要检查成功；若该工单包含发布，还须发布成功，才关闭 Issue 并同步 Project。PR 合并失败、验证阻塞或仅有本地文件时，保持 Issue 未完成。

必需检查为现有 CI 的 `test` 和 GitHub 原生提交状态 `acceptance`。后者是具备仓库权限的主持人的验收签收，不是自动认证审查者身份或测试质量。同账号团队不配置无法满足的 GitHub 自批 approval。

主持人先在 PR 评论记录已审完整 SHA、独立审查和实际验证证据，再从已审查的可信工作树运行[签收入口](../.github/acceptance.py)（参数见 `python3 .github/acceptance.py --help`）。入口核对当前 head 一致后，仅向传入的已审 SHA 发布成功状态并链接证据。新提交或更新分支后重新验收，不把旧证据关联到新 head；发布返回失败时，先核对 GitHub 上该 SHA 的实际状态，不盲目重试。

Issue 的原生依赖关系决定可开工顺序；Project 的 Status 只是 Issue 认领、阻塞、验收事实的投影，不以拖动卡片启动 Agent 或跳过验收。合并前不使用会提前关闭 Issue 的自动关闭关键词。规则、产品设计、具体任务验收分别只在本文、计划、Issue 保存一份。

## 开发团队与权限

| 职责 | 指定执行环境 |
| --- | --- |
| 并行实现与交叉审查 | Seedmux 真实 pane 中的 Kimi K3-256K（`--yolo`）、Cursor Grok 4.6 high fast、Claude Code Opus 5 medium |
| 浏览器实测 | 本地 agy Gemini 3.8 Flash high，通过 ego-browser 操作实际产品 |
| 派发、边界冻结、最终裁决 | 主持人 |

派发前以安装版本的帮助、模型清单和实际握手核对精确配置；模型不可用或启动器不支持参数就报告阻塞，不替换供应商、模型或权限模式冒名继续。Kimi 的 `--yolo` 不自动等于完全无人值守，不能改为 `--auto`；也不能因启动器默认值而扩大其他 CLI 的权限。

先用 seedmux-team 查看现场，复用空闲且上下文相关的 pane；不向权限弹窗或其他 waiting 状态注入任务。需要修改 Seedmux 或用户全局配置时另行取得授权，不在 Agora 复制另一套开发团队启动器。开发 pane 留给用户查看，不能作为产品自带 Worker 运行时交付。

浏览器实测必须记录候选提交、操作、预期与实际结果，附必要截图、console/network 证据并去除凭据。不以截图存在证明通过，不把模型名称写进报告就当作该模型实际执行。纯后端阶段记录浏览器项不适用及原因，以真实 CLI 和接口证据验收，不为测试临时造一个产品 UI。接入画布后，ego-browser 验证属于合入门。

## 编码与清理

- **深模块。** 小而稳定的接口封装能力、顺序约束和失败语义；业务逻辑不进入 UI、route handler 或 controller。进程内明确依赖直接调用，跨进程状态变化通过事件。只有稳定且语义相同的重复才抽象，不添加纯透传中间层。
- **单一事实源。** 业务规则、配置、schema 和任务状态各有一个权威位置。投影可重建且不能反向裁决；外部执行路径替换旧路径时清理旧执行状态机，不永久保留双写、兼容开关或旧引擎回退。
- **根因修复。** 定位问题后搜索同模式的写法与调用点，在触及范围内一并收口。交付记录写明搜索范围及剩余问题；不用消费端 guard、吞错、静默降级或假成功覆盖失败。
- **并发和等待。** 默认不可变；共享可变状态使用明确的锁、队列或原子操作。已有事件机制就订阅，不用 sleep、定时读文件或忙等待猜状态。
- **最小依赖。** 优先场景适配的最新稳定、轻量实现；已有依赖和标准库可满足时不新增生产依赖。新增需说明必要性、维护/体积/安全代价；不为追版本进行无关升级。
- **就地减法。** 行为变化同时删除失效分支、孤儿 import、旧配置和过时文档。测试只保护重要行为与可信回归；清理触及范围内重复、实现细节断言和无效用例，不为减少数量删掉行为保障。
- **可维护性。** 函数保持单一职责与同一抽象层级，用 early return 减少嵌套；复杂度超限时按职责重构，不机械拆行。魔法值提常量，注释解释非显然原因，不记录修改历史。

## 验证与工作树纪律

已有验证入口见[测试文档](testing.md)及项目配置。先跑受影响接口的最窄测试，再按依赖和风险扩大；仅项目门要求、影响无法可靠判断或窄测不足时跑全量。改测试时同步删除同范围低价值用例，不为文档变更启动数据库和真模型。

判断依据是原始命令退出码及实际覆盖。记录环境缺失、跳过、基线失败和模型费用；不能通过 `grep`、`head`、`tail` 或屏蔽错误把失败变成通过。真实终端语义不能只由假传输测试替代，浏览器测试也不能替代授权、消息事务和会话恢复验证。

开始和交付时读取 Git 状态并核对自己负责的差异，遇到并行或未提交改动继续，不擅自 reset、checkout、clean、rebase、stash 或切换他人的分支。仅暂存自己修改的路径，不用 `commit -a`。需要独立 worktree 时先确认提交基线和未提交资料如何交付，工作树隔离不等于允许破坏性 Git 操作。

行为、接口或流程变化同改事实源；README 面向用户，开发文档放在 `docs/`，重要模块的导航在 `AGENTS.md` 维护。PR 描述最终行为、实际验证和明确限制，不保存被淘汰方案、重复清单或未合入的修改历史。日志和测试证据不发布 token、认证文件或完整私有会话。
